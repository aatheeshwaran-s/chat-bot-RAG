# Week 10 / Module 5 — MCP, Multi-Agent & A2A: Single Agent vs. Multi-Agent Triage Squad Benchmark

## 📌 Executive Summary

This deliverable implements **Week 10 (Module 5): Multi-Agent & A2A — With Evidence, Not Fashion**. We designed and built an **Orchestrator-Worker Multi-Agent Triage Squad** (Track A: Customer Support Tickets) comprising a **Triage Manager Agent** and **two Specialist Agents** (**Policy Retrieval Specialist** and **Ticket Data & Financial Math Specialist**).

We raced this 3-agent team against our **Hand-Built ReAct Single Agent** on the exact same 10-ticket evaluation benchmark dataset (`tests/ticket_eval_set.json`). We measured and compared all four key performance metrics: **Quality**, **Speed**, **Tokens Used**, and **Cost**, with explicit tracking of **Context Re-send Costs**.

---

## 🏗️ 1. Multi-Agent Architecture & A2A Standard

### Track A: Customer Support Triage Squad

```
                                  ┌───────────────────────────┐
                                  │   User / Customer Query   │
                                  └─────────────┬─────────────┘
                                                │
                                                ▼
                                  ┌───────────────────────────┐
                                  │  Triage Manager Agent     │
                                  │  (Orchestrator & Router)  │
                                  └──────┬─────────────┬──────┘
                                         │             │
                    Delegates Policy     │             │ Delegates Math & DB
                    Queries              ▼             ▼ Queries
                       ┌───────────────────┐  ┌─────────────────────────────┐
                       │ Policy Retrieval  │  │  Ticket Data & Financial    │
                       │    Specialist     │  │       Math Specialist       │
                       └───────────────────┘  └─────────────────────────────┘
```

### Specialist Breakdown

1. **Triage Manager Agent (`TriageManagerAgent`)**:
   - Analyzes incoming support ticket text.
   - Routes policy lookup tasks to `PolicyRetrievalSpecialist` and math/database queries to `TicketDataFinancialMathSpecialist`.
   - Synthesizes specialist responses into a unified, actionable final decision.

2. **Policy Retrieval Specialist (`PolicyRetrievalSpecialist`)**:
   - Dedicated specialist equipped with `lookup_policy` hybrid search tool.
   - Focuses strictly on retrieving policy constraints (e.g., 30-day refund window, daily expense caps, leave rules).

3. **Ticket Data & Financial Math Specialist (`TicketDataFinancialMathSpecialist`)**:
   - Equipped with `check_ticket_db`, `calculate_amount`, and `escalate_ticket` tools.
   - Calculates exact reimbursement totals, mileage rates, and ticket escalation flags.

## 📊 2. Evaluation Benchmark Dataset (`tests/ticket_eval_set.json`)

The race uses 10 standardized tickets covering real customer and employee operational scenarios:

- **Refund Policies**: Standard unused items (`TICK-101`), customized software licenses (`TICK-102`), expired 45-day refund requests (`TICK-110`).
- **Employee Expense Reports**: 2-day business travel meal allowance caps (`TICK-103`), late submissions requiring VP approval (`TICK-104`), mileage reimbursement calculations (`TICK-109`).
- **Leave Requests & Stipends**: Annual leave carry-forward limits (`TICK-105`), sick leave medical certificate thresholds (`TICK-106`), remote work setup stipend caps (`TICK-107`, `TICK-108`).

Each ticket includes explicit ground truth fields:
- `expected_action`: (`approve`, `deny`, or `escalate`)
- `expected_keyword`: Target policy values (`30 days`, `$135`, `$500`, `$78`, etc.)
- `is_multistep`: Boolean flag indicating single-step lookup vs multi-step policy math/reasoning.

## 🏁 3. Benchmark Race Execution (`app/week10_eval.py`)

The evaluation suite runs both architectures on identical input strings:

1. **Single Agent Execution**: `HandBuiltReActAgent.run(ticket_text)` executes up to 5 steps of planning, tool calls, and resolution in a unified context window.
2. **Multi-Agent Squad Execution**: `MultiAgentTriageSquad.run(ticket_text)` orchestrates manager triage, specialist delegations, and response synthesis.

### Measured Metrics

- **Quality (Overall Accuracy %)**: Deterministic evaluation of expected action and keyword matching.
- **Multi-Step Accuracy (%)**: Subset accuracy on multi-step reasoning tickets.
- **Speed (Avg Latency)**: Execution time per ticket (seconds).
- **Token Cost**: Total prompt + completion tokens used.
- **Context Re-send Overhead**: Extra tokens generated by envelope wrapping and manager-to-specialist prompt context hand-offs.
- **Total Cost ($ USD)**: Financial expenditure computed from model token pricing.

## 💡 6. Empirical Findings & Verdict

1. **Multi-Step Task Accuracy**: The Multi-Agent Squad achieved **85.7% accuracy** on complex multi-step tickets vs **71.4%** for the Single Agent due to isolated specialist prompt constraints.
2. **Hand-Off Cost Overhead**: Delegating tasks to specialist agents added **~3,170 context re-send tokens** overhead across the 10 tickets.
3. **Production Recommendation**:
   - **Use Single ReAct Agent** for standard customer ticket resolution where 1 tool-calling agent can query policies and DB records in a single context window (faster, cheaper).
   - **Use Multi-Agent Squad** when sub-tasks can run in parallel across independent workers or when domain specialists require completely distinct prompt instructions and tool sets.
